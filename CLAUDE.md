# Imperium contributor guide

The source project is a static, single-player browser game. Read [reference requirements](docs/reference-requirements.md), [historical notes](docs/historical-research.md), the Contest rules sheet and the verification summary before changing game behaviour.

The current product and repository name is **Imperium** (`obeidpeter/Imperium`). Keep original names in archived evidence, exact generation prompts and supplied source-file citations. Retain legacy save/storage identifiers for compatibility, and distinguish the Latin military oath *sacramentum* from the former product name.

## Commands

Use Node.js 20 or later. The campaign rules have no runtime dependencies. The campaign 3D views and standalone study bundle Three.js 0.186.1 and its MIT license in `vendor/three/`, with the KTX2 (Basis Universal, Apache 2.0) and meshopt decoders it publishes; no package-install step or CDN is required.

- `npm run dev` — serve the source locally.
- `npm test` — run the Node.js rule tests.
- `npm run autoplay` — run the legal-command campaign harness.
- `npm run build` — build the static site into `dist/`.
- `npm run preview` — serve `dist/` through a plain static server.
- `npm run build:desktop` — build the same game for the desktop app into `dist-desktop/`: no service worker, offline packs or install manifest, and `platform: 'desktop'` in its configuration (`scripts/build.mjs --target desktop`).
- `npm run build:demo` — build the free web demo of Chapters I–III into `dist-demo/` (`scripts/build.mjs --edition demo`): the files only Chapters IV–XII use left out (`scripts/edition.mjs`), `edition: 'demo'` and its last chapter in its configuration, and `STORE_URL` as the full game's store page. `npm run preview:demo` serves it. The browser checks read `dist/`, the full game.
- `npm run verify` — run the tests, autoplay and production build.
- `npm run asset:tripo`, `npm run asset:process`, `npm run asset:bind`, `npm run asset:compress`, `npm run asset:check`, `npm run asset:preview`, `npm run asset:cc0` — the generated 3D asset pipeline (Tripo → Blender → the game): generate and rig with Tripo (network secret), process a prop or bind a character to the game's skeleton under Blender (`BLENDER_PYTHON` or `BLENDER`), compress it to KTX2 textures and meshopt geometry (`BASISU` and the glTF-Transform modules), check it against its budget, and render a review sheet (Playwright); fetch a CC0 texture set from Poly Haven or ambientCG with its licence and digests, and record a file made from it in the manifest. None of Blender, the compression tools or Playwright is a project dependency: `npm run asset:setup` installs them under `.tools/` in one command (`--check` reports without installing) and writes `.tools/env.ps1` on Windows or `.tools/env.sh` on Unix with the variables the scripts read. See [the asset pipeline](docs/asset-pipeline.md).
- `npm run benchmark:stage` — measure 3D battle start-up and play in headless Chromium: long tasks, shader programs (none may compile in the first frame or in play with `--check`), draw calls and triangles, through a legal exchange and a camera tour, and an estimate of the scene's texture and geometry memory. Software rendering: times are inflated, the stalls and counts are real. Needs Playwright like `npm run smoke`; `--dist` measures the production build. `--ceilings scripts/stage-ceilings.json` fails a run whose draw calls, triangles or shader programs rise above its recorded ceilings (CI checks Chapters V and XII); raise them only on purpose, with `--write-ceilings scripts/stage-ceilings.json`, and record why.
- `npm run benchmark:arena` — measure the 0.40 real-time arena in headless Chromium: start-up, click-to-first-movement in milliseconds and frames, whole fights won by one click per raider, and the arena's own performance check. Needs Playwright like `npm run smoke`; `--dist` measures the production build, `--write` saves `docs/evidence/arena-phase0.json`.
- `npm run guide:help` — regenerate the in-game Controls & rules (`src/data/guide-help.js`) from `docs/player-guide-0.40.md` after editing the guide; a test fails while they differ.
- `node scripts/steam-achievements.mjs` — regenerate the Steamworks achievement sheet (`docs/steam-achievements.md`) from `src/data/achievements.js` after changing the achievements; a test fails while they differ.
- `node scripts/kit-audit.mjs` — regenerate the kit audit (`docs/kit-audit.md`) after changing items, containers, champions, the armourer's or quartermaster's stock, pay or errands; a test fails while it differs. `node scripts/tp-audit.mjs` does the same for the training-point audit (`docs/tp-audit.md`).
- `node scripts/realtime-sweep.mjs` — the real-time calibration sweep (development only): the bot plays the campaign from New Game on campaign seeds and checks the plan's targets. `--difficulty=story|standard|veteran`, `--kit=bare|issued|engaged` (the reference players of `scripts/kit-policy.mjs`), `--first=1 --last=12` (the chapters it counts), `--seeds=20`, `--label=… --write` (saves `docs/evidence/realtime-<label>-sweep-<difficulty>[-<kit>].json`). Tick times are fair only from one sweep at a time on one machine.
- `node scripts/upgrades-check.mjs --label=<label>` — the plan's "upgrades count" target on a release's six sweeps (Story bare and issued, Standard and Veteran issued and engaged): on Veteran, engaged ends its wins in Chapters I–III and the champion battles with at least 3 points more health and 0.3 rounds sooner than issued; on Story, issued ends the champion battles with at least 10 points more health than bare. It exits 1 if a target is not met; `npm test` checks release 11's sweeps.
- `npm run smoke` — drive the production build in headless Chromium (New Game, walking, Confirm moves, a restored expanded field, a field approach with Chapter V's generated scenery and character bodies loaded in 3D, phone touch, the Settings performance check; in real time, the arena, Chapter I's camp, drill and field, squads and deployment, the chamber Contests, the finale, the settings and help, and an old chronicle). Run `npm run build` first. It needs Playwright, which is not a project dependency: install it separately or set `PLAYWRIGHT_MODULE`. `SMOKE_ONLY=name,…` runs the named scenarios; `SMOKE_GROUP=a` or `b` runs one half, as CI's two parallel smoke jobs do (the script names group a; group b is every other scenario). `SMOKE_CPU_THROTTLE=4`, for this and every other browser check, slows the page's CPU fourfold through the DevTools protocol, about as slow as a busy CI runner, to find a step that races a short message or a slow frame before CI does; a check that reads the bar's event line records it with `watchEventLine`, and the card naming the next area with `watchAreaCards` (`scripts/ui-smoke-navigation.mjs`). CI runs it on every pull request.
- `npm run smoke:polish` — the real-time playtest regressions in headless Chromium (`scripts/realtime-polish-smoke.mjs`): live target forecasts, Pause with the command list open, Home clearing the previous target, the rescue's planning pause and wording, unobstructed layouts at 580- and 1,280-pixel widths (Chapter V and the council), and the equipped-soldier preview. Build first; needs Playwright like `npm run smoke`. Reports go to `tests/visual-results/realtime-polish/`; CI runs it after the smoke test.
- `npm run smoke:cavalry` — an earned Chapter IX checkpoint in headless Chromium: select cavalry, issue Charge and Feigned retreat with default and remapped keys, check the accessible card, and preserve the paused world after invalid inputs. Build first; needs Playwright. Reports go to `tests/visual-results/cavalry-controls/`; CI runs it after the real-time controls check.
- `npm run smoke:usability` — the simplified interface's player flows in headless Chromium (`scripts/usability-smoke.mjs`), at desktop and 390-pixel widths: the Menu and Settings categories with keyboard focus, 200% text and high contrast, help search, keyboard access to grouped actions, menu pause and save confirmation. Build first; needs Playwright. Reports and screenshots go to `tests/visual-results/usability/`; CI runs it as its own job.
- `npm run smoke:navigation` — New Game's required steps in headless Chromium (`scripts/playtest-navigation-smoke.mjs`), at 1,280 and 390 pixels wide: the folded setup, the camp map's numbered places, **Walk there** before a visit and **Fast travel** only after one, **Show me the way** to the commander's table, then, after the decision, to the way out without using it. Build first; needs Playwright. Reports go to `tests/visual-results/playtest-navigation/`; CI runs it after the usability checks.
- `npm run smoke:desktop` — the desktop app for Steam (`desktop/`; [docs/desktop.md](docs/desktop.md)) driven through its interface by Playwright's Electron support (`scripts/desktop-smoke.mjs`): its `app://imperium` origin and bridge, Settings' Fullscreen, New Game to the first camp with the save written as a file, Quit after the save, and a relaunch with only the save file. No request may leave the app's origin. Build first (`npm run build:desktop`) and install the app's packages (`cd desktop && npm ci`); `DESKTOP_APP=packaged` drives the packaged app (`npm run package:linux` or `package:win` in `desktop/`). On Linux without a display run it under `xvfb-run -a`; as root (a container) it passes `--no-sandbox`. CI runs it on Linux and Windows.
- `npm run smoke:demo` — the demo build in headless Chromium (`scripts/demo-smoke.mjs`): its title, a Chapter IV save code refused, Chapter III's promotion as the End of the demo, and a kept code the full game advances, with no failed request. Build first (`npm run build:demo`); needs Playwright. Reports go to `tests/visual-results/demo/`; CI runs it.
- `npm run smoke:ch5-pilot` — Chapter V's staging courtyard and fortress in headless Chromium (`scripts/ch5-pilot-smoke.mjs`), from checkpoints earned by legal commands and restored through the visible interface: every pilot scenery placement in Balanced 3D, the peaceful courtyard's refusals, the engineer's preparation handoff, the decision through export and restore, March out and an exact Retry; `--river-gate` also departs for the red river gate. Build first; needs Playwright. Reports go to `tests/visual-results/ch5-pilot/`; CI runs it after the usability checks.
- `npm run smoke:world` — all twelve camps in one browser context (`scripts/regional-world-smoke.mjs`): each chapter's regional models and the three cameras, direct services and peaceful controls, narrow layouts, scenery released between chapters and on Performance, and a camp that still works when every model download fails. `--half a` (Chapters I–VII, with Chapter I's services, the return and the failed downloads) and `--half b` (VII–XII, with VIII's and XII's services and Performance) are the two halves CI runs in parallel; together they are the full acceptance, and Chapter VII is in both so every move from one camp to the next is checked in one context. `--chapters 1,8` is a partial diagnostic, not acceptance; `--checkpoints-only` only earns the review saves. Build first; needs Playwright. Reports go to `tests/visual-results/regional-world/` (a half's to `half-a/` or `half-b/` in it); CI runs the halves as two jobs.

Check `package.json` for the authoritative current scripts. Build configuration, including the site address, belongs in the shared configuration/build boundary rather than hard-coded host URLs scattered through the game. Publishing, DNS and live-phone checks are the owner's next deployment steps.

## Module boundaries

- `src/core/` owns the deterministic rules, legal commands, seeded RNG, encounter transactions, campaign progress and derived access rules. It must not import browser UI, rendering, Canvas, audio, storage, network, timers, wall-clock time or `Math.random`.
- `src/core/realtime/` is the 0.40 real-time simulation (build brief: `docs/realtime-survey.md`, `docs/player-guide-0.40.md`): a fixed 20 Hz tick, Commands queued for the next tick boundary, named random streams split from the campaign's seeded generator, and an exact JSON snapshot with a world hash. It never reads the clock or frame time; the page's fixed-step driver (`clock.js`) decides only how many ticks run. Its rules are data in `src/data/realtime-rules.js`. `src/core/controls-model.js` decides which encounters play in real time; the 0.38 turn path stays playable until Gate 4.
- `src/data/` contains structured chapter, mission, decision, dialogue, historical and balance data. Prefer data additions over chapter-specific engine branches. The companion technical specification calls this boundary `src/content/`; this project currently names it `src/data/`.
- `src/ui/renderer.js` draws the world, units and portraits from state; it must not mutate campaign or encounter state.
- `src/ui/` and the browser shell expose accessible input, previews, screens and feedback. All gameplay mutations go through the rules command API.
- Browser-only storage, offline caching and sharing belong at the platform boundary, outside the rules core.
- `src/ui/platform.js` is that boundary between the web site and the desktop app: everything that differs between them asks it (the offline cache, save files, Quit, fullscreen, wording, connection checks). The desktop build's `CONFIG.platform` and the app's bridge (`window.imperiumDesktop`) decide; without the bridge a desktop build behaves as the web. The web demo's edition is asked there too (`demoEdition()`): its last chapter comes from the build, never the save, and the rules refuse to advance past it (`advanceChapter(state,{lastChapter})`).
- `desktop/` is the desktop app for Steam (Electron), a separate package so the web project stays dependency-free. It owns the window, the save files and Steam (`desktop/steam.cjs`, steamworks.js, only with a Steam App ID); the page reaches it only through the sandboxed preload bridge. Achievements are read from the chronicle by `src/core/achievements.js`, a pure function that never grants anything. It serves the game under one fixed origin, `app://imperium`: never change it, since the page's saves belong to it.
- `scripts/` contains build, local serving and automation tools. `tests/` verifies rules and recovery behaviour under Node.
- `docs/` records rules, provenance, verification and limitations. Private business source documents are not included in the distribution.

## Invariants and review

Invalid commands and previews must leave the entire state, including the random generator, unchanged. Never grant victory, promotions or milestones directly from an autoplay script or UI handler. Autoplay starts at New Game and uses legal commands; any injected scenario is labelled separately.

An encounter owns a complete start snapshot. Stage effects until final resolution, record a unique commit, and restore the start snapshot on retry. A reload cannot duplicate rewards, promotions or Obligations. Derive chapter access from completed milestones rather than a saved unlock flag. Preserve incompatible saves instead of silently deleting them.

Do not remove the finale's recovery floor or punish higher meters by taking away routes. A named companion's permanent fate must come from a clearly signalled decision or authored outcome, not uncontrolled allied AI.

Every recorded narrative choice needs a later visible consequence; every potentially absent cast member needs an absence or replacement branch. The oath must use one shared content entry at both ends of the campaign. Major public history remains fixed through Aurelian's death in 275; the succession then deliberately diverges.

The approved visual direction combines locally bundled original/AI-generated illustration with code-drawn tactical terrain, units and overlays. Since 0.37 the 3D figures wear generated character bodies (see the asset pipeline) over the code-built rig, kit and animation; the code-built figures remain the fallback. Record asset provenance, rights limitations and export settings in docs/asset-manifest.json and docs/art-generation.md. Do not add unlicensed third-party art, font or audio files. Keep the site static and free of accounts, payment, advertising or analytics integrations unless separately requested. The owner has requested a Steam release ([docs/steam-plan.md](docs/steam-plan.md)): Steam's integrations live in `desktop/` only, and the web build stays static. Presentation must never mutate game state or consume gameplay randomness.

The companion technical document specifies strict TypeScript, Vite, Vitest and Playwright. The current JavaScript/custom-build stack is an explicit implementation deviation; its campaign WebGL views and standalone study use locally bundled Three.js. Do not describe the project as satisfying the specified stack requirement or claim unperformed browser/device, accessibility, timing or deployment checks.

For review reports, distinguish automated tests, real-interface play, injected scenario tests and real devices. Record meaningful limitations plainly. The 90–150 minute target needs human playtesting.
